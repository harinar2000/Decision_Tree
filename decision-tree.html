// Decision Tree — start at Q1
Q1
Does this task require reading or writing data in an external system (CRM, calendar, DB, API, file system)?
NO → Task is self-contained. Go to Q2. → Q2
YES, once → Single external call — one system, one operation. Go to Q3. → Q3
YES, multi → Reads/writes across multiple systems or requires sequencing decisions across steps. SUB-AGENT
Q2
Is this task reused across teams, products, or sessions — or does it need enforced consistency?
NO, one-off → Bespoke instruction for this session. Write inline. No overhead justified. PROMPT
YES, shared → Shared behavior that multiple agents or products will call. Package it. Version it. SKILL
Q3
Is the integration real-time, bidirectional, or stateful — or does it just need to call a third-party API once?
Simple call → Single-direction, stateless API call. Search, lookup, fetch. Scope is narrow. PLUGIN
Stateful / rich → Needs context, session state, or exposes multiple operations from one system (Jira, Salesforce, Slack). MCP
Q4
Override check: Does the task require parallelism, long-horizon planning, self-correction, or spawning child tasks?
NO → Stick with what Q1–Q3 pointed to. Single-layer is fine. HOLD
YES → Upgrade to Sub-agent regardless of prior answers. Complexity demands autonomous orchestration. SUB-AGENT
// Tool Reference — what each one is, when it wins, when it loses
Prompt
What it is
Natural language instruction — inline or system. Ephemeral. Scoped to one session or one call.
Use when
Task is bespoke, one-off, or exploratory. No reuse. No external calls. Fast iteration needed.
Don't use when
Same logic is repeated. Multiple agents need consistency. Behavior needs to be tested and versioned.
Effort
Minutes. No infrastructure.
Skill
What it is
Packaged, versioned prompt-plus-context. A reusable module that agents invoke. Lives in a registry or repo.
Use when
Same capability is needed across multiple products, agents, or teams. Needs consistent behavior and testability.
Don't use when
Task is truly one-off. Overhead of packaging isn't justified. Skill library doesn't exist yet.
Effort
Hours to build, maintained over time. Requires SKILL.md + eval harness.
Plugin
What it is
Stateless function that calls a third-party API. Narrow scope. No memory. Request → response.
Use when
Single-operation external call: search, weather, lookup, price fetch. Scope won't expand.
Don't use when
You need session state, multiple operations on one system, or auth/context per user. Use MCP instead.
Effort
Low–medium. Write tool spec + schema. No server needed.
MCP
What it is
Model Context Protocol server — exposes multiple tools from one system with session context, auth, and shared state.
Use when
Integration needs depth: create + read + update in one system (Salesforce, Jira, Slack). Auth is per-user. State matters.
Don't use when
You only need one stateless API call. Plugin is cheaper and simpler. MCP overhead isn't earned.
Effort
Medium–high. Server infrastructure + tool definitions + auth layer.
Sub-agent
What it is
Autonomous agent spawned by an orchestrator. Has its own context, tools, and loop. Reports result back.
Use when
Task is too complex for one agent: parallelism needed, multi-system writes, long-horizon planning, self-correction loops.
Don't use when
Task fits in one context window. Debugging compound agents when simpler tools would work is expensive.
Effort
High. Orchestrator + harness + AGENTS.md + eval loops. Only justified for genuinely compound tasks.

// Tiebreakers — when two answers look right
Prompt vs. Skill — both seem fine?
Ask: will a second team or a second product ever need this exact behavior? If yes → Skill. If no → Prompt. Don't over-engineer a one-off.
Plugin vs. MCP — feels like either could work?
Count the operations. One operation, no state → Plugin. Two or more operations, or user-scoped auth → MCP. When in doubt: start Plugin, upgrade to MCP when scope creeps.
MCP vs. Sub-agent — where's the line?
MCP gives Claude tools. Sub-agent gives Claude an agent. If you need decisions between external calls — not just execution — you need a sub-agent, not more MCP tools.
Skill vs. Sub-agent for repeatable tasks?
Skill = packaged reasoning pattern, no autonomy. Sub-agent = autonomous executor with its own tools. Use Skills inside Sub-agents for reuse without coupling architecture to behavior.
My use case is regulated (pharma). What changes?
Sub-agents and autonomous MCP writes need a human-in-the-loop gate before any system of record mutation. Prefer read-heavy MCP + human confirmation patterns. Prompts + Skills are low-risk.
Complexity is unclear. Where do I start?
Start with a Prompt. If it needs reuse → promote to Skill. If it needs external data → add Plugin or MCP. If it needs to orchestrate → graduate to Sub-agent. Never build Sub-agent-first.
